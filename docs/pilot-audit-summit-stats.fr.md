Suite du pilote GeoChallenge-Tracker (`docs/pilot-audit-geochallenge-tracker.md`), exécuté à la demande de l'utilisateur pour vérifier si les mécanismes et constats du Quality Framework v1.0 tiennent sur une stack structurellement différente : Laravel/PHP + Vue/JS simple (Summit-Stats) contre FastAPI/Python + Vue/TS (GeoChallenge-Tracker). ## 3. Constats de calibration — faux positifs et corrections d'invocation d'outils

Comme pour GeoChallenge-Tracker, c'est la vraie valeur de cette passe : les endroits où le framework figé ou la chaîne d'outils validée ont besoin d'une correction, plus des vérifications explicites de cohérence inter-dépôts contre les constats du premier pilote.

### 3.1 Gitleaks : le motif de faux positif des fichiers d'exemple de config revient exactement comme documenté pour GeoChallenge-Tracker

Le constat unique de Gitleaks est une correspondance `generic-api-key` sur `.env.prod.example` (un fichier modèle, pas un vrai fichier d'environnement — correspondance sur une valeur comme `BCRYPT_ROUNDS=12`, pas un vrai secret). Même classe déjà signalée dans la recommandation §3.1 du premier pilote (pré-filtre de fixture de test pour P1). **Signal de cohérence inter-dépôts :** ceci confirme que le motif de faux positif n'est pas spécifique au style de token de test de GeoChallenge-Tracker — il se généralise à tout fichier de config exemple/modèle avec des valeurs d'apparence plausible. Recommande d'élargir la correction §3.1 des motifs « fichier de test » pour aussi couvrir les motifs de chemin de fichier `.env.*.example`/`.env.*.template`/`.env.*.sample`.

### 3.2 Larastan est incompatible avec le motif d'installation éphémère/détenue-par-l'audit (D7) — cause racine confirmée, correctif validé

Installer PHPStan + Larastan dans un projet Composer scratch détenu par l'audit (selon « l'audit pinne/installe ses propres versions d'outils indépendamment du dépôt cible » de D7) et le pointer vers `app/` de Summit-Stats via un chemin absolu échoue avec `Undefined constant "Larastan\Larastan\LARAVEL_VERSION"`. Ce n'est **pas** un problème de périmètre de scan — exclure `vendor/`/les dossiers de framework des `paths` analysés n'y change rien, parce que l'échec se produit pendant le parsing de `extension.neon` de Larastan, avant même qu'un seul fichier ne soit sélectionné pour analyse. Le mécanisme réel : Larastan résout la version Laravel de la cible et charge le jeu de stubs correspondant en introspectant le propre `vendor/`/`composer.lock` installé de l'app — un projet Composer scratch sans rapport n'a rien à introspecter, quel que soit le chemin scanné.

**Correctif confirmé par test direct :** ajouter temporairement `larastan/larastan` comme `require-dev` dans le propre `composer.json` de Summit-Stats (`composer require --dev phpstan/phpstan larastan/larastan --no-interaction`), exécuter `vendor/bin/phpstan` depuis là avec un include `extension.neon`, puis annuler `composer.json`/`composer.lock` et relancer `composer install` pour restaurer le dépôt exactement comme il était (vérifié propre via `git status` avant et après). Résultat : les 87 file_errors majoritairement du bruit du fallback PHPStan simple sont tombés à **12 file_errors de vrai signal** — une constante de classe inutilisée, des discordances de type générique sur deux types de retour de relation Eloquent, un problème potentiel d'appel null-safe sur `toDateTimeString()`, et des avertissements de paramètre par référence dans `StatsAggregatorService`. C'est une véritable exception, maintenant documentée, à D7 : l'analyse statique Laravel-aware nécessite structurellement de s'exécuter à l'intérieur du propre arbre de dépendances de la cible, pas le motif entièrement isolé qui fonctionne pour tout autre outil PHP éphémère. **Correction appliquée à `toolchain.md` :** documentée, y compris l'étape d'annulation afin que l'audit ne laisse jamais d'empreinte dans le dépôt scanné.

### 3.3 Chaque outil PHP éphémère a besoin de son propre projet Composer scratch isolé

Installer PHPMD dans le même répertoire scratch déjà utilisé pour PHPStan+Larastan a causé un conflit de dépendances Composer fatal (`PDepend\DependencyInjection\PdependExtension::load(...)` incompatible avec la version Symfony DI que l'arbre de Larastan a tirée) — pas un bug de PHPMD, un clash de dépendance transitive entre deux outils sans rapport partageant un `vendor/`. **Correctif :** un tout nouveau projet scratch entièrement isolé (`/tmp/phpmd-scratch`, PHPMD uniquement) s'est résolu proprement. **Correction nécessaire pour `toolchain.md` :** chaque outil PHP éphémère (PHPStan, PHPMD, Pint si jamais exécuté de façon autonome, etc.) doit obtenir son propre projet Composer scratch isolé — jamais partager un `vendor/` entre plusieurs outils d'analyse statique, même si c'est plus de charge de setup que le côté JS/TS (où `npx <tool>` évite l'équivalent de ce problème avec un `node_modules` partagé).

### 3.4 `.claude/worktrees/` est un piège de découverte récursive généralisé, pas un cas particulier limité aux Dockerfiles

La Phase 1 n'a documenté ceci que pour la découverte de Dockerfile. Cette passe a trouvé que cela casse indépendamment deux autres outils sur le même dépôt :
- **Vitest** a silencieusement compté deux fois chaque test (62 réels → 124 rapportés) parce que le `test.exclude` de `vitest.config.js` couvre `node_modules/**` et `e2e/**` à la racine du dépôt, mais pas `.claude/worktrees/**`, qui contient sa propre copie imbriquée à la fois de `resources/js/__tests__/` et de `e2e/`.
- Pire que le double comptage : `npm run test:coverage` (qui invoque le run Vitest complet sans filtre de chemin) **échoue durement** avec `Playwright Test did not expect test.describe() to be called here` — Vitest ramasse `.claude/worktrees/.../e2e/upload.spec.js`, un fichier de spec Playwright, et plante sur la discordance d'API `test.describe()` entre les deux exécuteurs de test. Ce n'est pas un double comptage cosmétique, c'est un échec de run complet.
- Le scan **Trivy fs** a de même compté deux fois des CVE depuis `composer.lock`/`package-lock.json` dupliqués à l'intérieur du worktree.

**Correctif utilisé cette passe (ad hoc) :** filtrage du JSON de résultat pour exclure tout chemin contenant `.claude/worktrees`, et relance séparée de Vitest recadré explicitement sur `resources/js` (`npx vitest run --coverage resources/js`) pour contourner entièrement le crash Playwright. **Vrai correctif, confirmé après coup :** c'est entièrement filtrable par outil, pas un cas nécessitant un fallback manuel/skip-tool. Chaque outil de cette chaîne qui scanne récursivement a un mécanisme d'exclusion natif, vérifié directement contre le propre `--help` de chacun : `find` (`-not -path`), Vitest (`--exclude <glob>`), `trivy fs`/`trivy image` (`--skip-dirs`), dependency-cruiser (`-x/--exclude <regex>`), ESLint (`--ignore-pattern`), PHPMD (`--exclude`), PHPStan (`excludePaths` dans sa config neon). La liste d'exclusion ne doit pas non plus être codée en dur sur `.claude/worktrees` — `git worktree list --porcelain` donne les chemins exacts de worktree pour n'importe quel dépôt, donc l'audit peut calculer la liste d'exclusion une fois par dépôt et l'injecter dans quel que soit le mécanisme que chaque outil supporte. **Correction appliquée à `toolchain.md` :** la note existante limitée à la découverte de Dockerfile a été généralisée en cette règle valable pour tout le dépôt, avec les flags natifs d'exclusion confirmés pour chaque outil scannant récursivement dans la chaîne et l'approche `git worktree list --porcelain` pour calculer dynamiquement la liste d'exclusion par dépôt, plutôt que de coder en dur `.claude/worktrees`. Ceci est maintenant confirmé sur 2/2 dépôts pilotés qui se trouvaient avoir un worktree actif au moment de l'audit.

### 3.5 Un `coverage.xml` committé peut être périmé et trompeur — toujours régénérer plutôt que faire confiance à un artefact versionné

Le `coverage.xml` committé du dépôt montrait 537/726 instructions couvertes (73,97%), ce qui se lirait comme *en dessous* du propre gate CI à 80% du dépôt — un constat inquiétant au premier regard. Relancer `vendor/bin/pest --coverage` fraîchement a produit 91,4%, confortablement au-dessus du gate. Le fichier committé était simplement périmé (d'un point antérieur de l'historique du dépôt, non régénéré depuis). **Correction nécessaire pour `toolchain.md`/l'orchestration :** les critères de couverture (3.1, et tout futur critère de seuil de couverture) doivent toujours régénérer la sortie de couverture depuis un run de test en direct, jamais lire un `coverage.xml`/`coverage-summary.json` versionné comme vérité terrain, même quand il est présent dans le dépôt. Mérite une note d'une ligne dans la section Testing de `toolchain.md` — c'est un constat nouveau, non documenté auparavant depuis la passe de GeoChallenge-Tracker (le % de couverture de GCT avait déjà été signalé là-bas comme « non extrait cette passe », ce qui rétrospectivement était le défaut le plus sûr).

### 3.6 Le bruit de PHPStan-sur-Eloquent est de la même classe structurelle que le bruit d'ESLint-sur-artefacts-générés de GeoChallenge-Tracker

Les deux sont des cas où « la sortie brute d'outil a besoin d'une config sensible au domaine ou d'un filtrage de périmètre avant d'être fiable pour la notation » : les 42 erreurs ESLint de GCT étaient 100% du bruit provenant d'artefacts `.venv`/`htmlcov` scannés accidentellement ; les 87 file_errors PHPStan de Summit-Stats (sans Larastan) sont majoritairement du bruit provenant de la magie dynamique `$model->property` d'Eloquent et des fonctions helper globales de Laravel (`config()`, `request()`, `database_path()`) non reconnues sans les fichiers de stub de Larastan. Cause racine différente (stubs Laravel-aware manquants contre mauvais périmètre de scan), même leçon : PHPStan sans Larastan sur un dépôt Laravel ne devrait pas être fiable pour un score de complexité/qualité 2.x. Avec le correctif du §3.2 appliqué, le bruit disparaît (12 vrais constats au lieu de 87), donc c'est maintenant un cas résolu plutôt qu'une mise en garde ouverte.

## 5. Évaluation de la cohérence inter-dépôts

Répondre à la question pour laquelle ce second pilote a été exécuté : le Quality Framework v1.0 se comporte-t-il de façon cohérente à travers deux dépôts structurellement différents ?

**Oui, avec une confiance élevée.** Preuves concrètes :

1. **Le mécanisme de pénalité critique P2 s'est déclenché indépendamment sur les deux dépôts**, à chaque fois via deux sources de preuve séparées (GCT : image Trivy + la vérification croisée de disponibilité-de-correctif de la première passe ; Summit-Stats : npm audit + image Trivy, sur le même type de couche Alpine/Node que les deux dépôts partagent sur leur frontend). C'est le mécanisme aux enjeux les plus élevés du framework (il plafonne le score d'une catégorie entière) et il s'est déclenché correctement, pour la bonne raison, sur des arbres de dépendances sans rapport les deux fois.
2. **La classe de faux positif de fichier d'exemple de Gitleaks est revenue exactement**, renforçant (pas juste confirmant) la recommandation §3.1 du premier pilote — c'est maintenant clairement un motif méritant un vrai pré-filtre, pas une bizarrerie isolée de la suite de tests de GCT.
3. **Un mode d'échec structurellement identique de « la sortie brute d'outil a besoin de conscience de périmètre » est revenu** (§3.6) avec un outil différent et une cause racine différente, suggérant que c'est une propriété générale de l'outillage d'analyse statique sur de vrais dépôts, pas quelque chose de spécifique à Python/JS.
4. **Des constats vraiment différents, spécifiques au dépôt, notés comme attendu** plutôt que de retomber sur des chiffres similaires : 13.1/13.3 (migrations/factories) sont passés du 0/À FAIRE de GCT au 10 de Summit-Stats, reflétant exactement la vraie différence entre une app MongoDB sans schéma et une app Laravel/Eloquent — le framework n'a pas aplati une vraie différence architecturale en une fausse équivalence.
5. **Un constat nouveau et précieux a émergé que la passe de GCT n'avait pas fait remonter** : le piège de découverte `.claude/worktrees/`, précédemment limité à la découverte de Dockerfile en Phase 1, est maintenant confirmé comme un risque général de découverte récursive (Vitest, Trivy fs) — exactement le genre de généralisation qu'un second pilote est censé attraper qu'un pilote unique ne peut pas.

Aucun changement de taxonomie, de poids, ou de modèle de notation n'est justifié par cette passe. Tous les constats du §3 sont des corrections de précision d'invocation de la chaîne d'outils (exigence d'installation in-repo de Larastan, projets Composer scratch isolés, exclusion de worktree, régénération de couverture), la même catégorie de correction que le premier pilote a produite — renforçant que le travail de la Phase 3 (durcir les invocations avant que la Phase 4 ne les automatise) est sur la bonne voie, pas que le framework lui-même a besoin d'être retravaillé.

## 6. Corrections de framework recommandées (pour `quality-framework.md` / `toolchain.md`)

Les six corrections ci-dessous ont toutes été appliquées directement à `quality-framework.md`/`toolchain.md` à la date de cette passe (pas laissées comme travail futur) :

1. **Condition P1 de `quality-framework.md`§3.2** — élargissement du pré-filtre de fixture de test dérivé de GCT pour aussi couvrir les motifs de chemin de fichier `.env.*.example`/`.env.*.template`/`.env.*.sample`, selon le §3.1 ici. Appliqué.
2. **Section PHP/Laravel de `toolchain.md`** — remplacement de la note ouverte « décision de config nécessaire » par le correctif confirmé du §3.2 : Larastan doit être installé temporairement dans le propre `vendor/` de la cible (pas le motif scratch isolé de D7), avec l'étape d'annulation exacte afin qu'aucune empreinte ne soit laissée dans le dépôt scanné. Appliqué.
3. **Section PHP de `toolchain.md`** — documentation de l'exigence de scratch isolé par outil du §3.3 : ne jamais partager un projet Composer scratch entre plusieurs outils d'analyse statique éphémères. Appliqué.
4. **Section Conteneurs de `toolchain.md`** — généralisation de la note existante limitée aux Dockerfiles sur `.claude/worktrees` (§3.4) en une règle d'exclusion valable pour tout le dépôt, avec le flag natif d'exclusion confirmé pour chaque outil scannant récursivement dans la chaîne et l'approche `git worktree list --porcelain` pour calculer dynamiquement la liste d'exclusion par dépôt, plutôt que de coder en dur `.claude/worktrees`. Appliqué.
5. **Section Python de `toolchain.md`** — ajout d'une règle inter-langages selon laquelle les critères de couverture doivent toujours régénérer depuis un run de test en direct, jamais faire confiance à un `coverage.xml`/`coverage-summary.json` versionné (§3.5). Appliqué.
6. **`quality-framework.md`§3.5 (nouvelle sous-section, « Fraîcheur de la preuve »)** — formalisation de la règle de régénération de couverture comme règle de méthodologie globale, pas juste une note opérationnelle de `toolchain.md` : tout critère dont la preuve pourrait être lue depuis un artefact versionné et généré par un outil doit à la place provenir d'un run en direct effectué par l'audit lui-même. Appliqué.

Aucune de ces corrections n'est un changement de taxonomie ou de modèle de notation. Combinée aux quatre corrections du premier pilote, la Phase 3 a maintenant produit neuf corrections d'invocation de chaîne d'outils concrètes et étayées par des preuves à travers deux stacks structurellement différentes — une base solide pour cocher la case restante de la Phase 3 (« Confirmer le Quality Framework v1.0 comme référence pour le premier audit global ») une fois ces corrections intégrées.
